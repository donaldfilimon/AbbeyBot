# Serve Dashboard SPA from AbbeyServer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve the built React dashboard SPA (`web/`) as static assets from the existing `AbbeyServer` Vapor process at `/dashboard`, with one Docker image and no CORS, instead of a separately hosted frontend.

**Architecture:** Vite's build output is redirected to land directly inside `AbbeyServer`'s existing SwiftPM resource directory (`Sources/AbbeyServer/Resources/Public/`), which SPM already copies verbatim via `Package.swift`'s `.copy("Resources")` — no Package.swift change needed. Vapor's `FileMiddleware` serves the static assets (JS/CSS/etc.) directly by request-path match; one explicit route serves `index.html` at `/dashboard`. The Dockerfile gains a Node build stage that runs before the existing Swift build stage, since the SPM resource files must exist on disk before `swift build` copies them.

**Tech Stack:** Vapor `FileMiddleware`, Vite (`build.outDir`), Docker multi-stage build, Bash/curl smoke testing (this repo's existing test idiom for the server — see `Scripts/run-server-smoke.sh`; there is no XCTVapor test target for `AbbeyServer` today and this plan doesn't introduce one).

## Global Constraints

- Swift 6.4 / `.swiftLanguageMode(.v6)` on every SPM target (from `Package.swift`).
- `AbbeyServer`'s existing routes (`/health`, `/api/*`, `GET /` Leaf status page) must keep working unmodified — the dashboard is additive, mounted at `/dashboard`, not a replacement for `/`.
- No new SPM dependencies. No new top-level npm/bun dependencies beyond what `web/` already has from its own scaffold.
- Follow this repo's existing test idiom: server-side behavior is verified via `Scripts/run-server-smoke.sh` (bash + curl assertions against a live local instance), not a new unit-test framework.
- This plan assumes `web/` already exists with a working Vite + React + TypeScript scaffold whose `package.json` has a `build` script producing a standard Vite output (`index.html` + an `assets/` directory) — it does not depend on any of `web/`'s internal component code, only on that standard Vite build contract.

- [ ] **Step 2: Add the `/dashboard` route**

Modify `Sources/AbbeyServer/Routes/routes.swift` — add this route inside `func routes(_ app: Application) throws { ... }`, placed right after the `app.get("health") { ... }` route (so it's grouped with the other top-level, non-`/api` routes):

```swift
    app.get("dashboard") { req async throws -> Response in
        let publicDir = Bundle.module.bundleURL
            .appendingPathComponent("Resources")
            .appendingPathComponent("Public")
        let indexPath = publicDir.appendingPathComponent("index.html").path
        guard FileManager.default.fileExists(atPath: indexPath) else {
            throw Abort(.notFound, reason: "Dashboard not built — run `npm run build` in web/ first")
        }
        return req.fileio.streamFile(at: indexPath)
    }
```

```swift
import AbbeyCore
import AbbeyServerKit
import Foundation
import Vapor
```

### Task 3: Multi-stage Dockerfile builds the SPA before the Swift build

**Files:**
- Modify: `Dockerfile`

**Interfaces:**
- Consumes: `web/package.json`'s `build` script (produces output at `Sources/AbbeyServer/Resources/Public/` per Task 1's `vite.config.ts`).
- Produces: the final `runtime` stage's copied resource bundle (`AbbeyServer_AbbeyServer.resources`) includes `Public/` alongside the existing `Views/`, since SPM's `.copy("Resources")` (already declared in `Package.swift`, unchanged) copies the whole `Resources/` directory recursively.

- [ ] **Step 1: Read the current Dockerfile**

Current full contents:

```dockerfile
# syntax=docker/dockerfile:1
# Build with official Swift 6.4 bookworm image (Linux) — must match Package.swift's
# swift-tools-version: an older toolchain's SwiftPM cannot parse a newer manifest.
# Leaf resources ship via SPM bundle.

FROM swift:6.4-bookworm AS build
WORKDIR /build
COPY Package.swift Package.resolved* ./
COPY Sources ./Sources
COPY Tests ./Tests
RUN swift package resolve
RUN swift build -c release --product AbbeyServer

FROM debian:bookworm-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates \
    libcurl4 \
    libssl3 \
    libsqlite3-0 \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=build /build/.build/release/AbbeyServer /app/AbbeyServer
# SPM resource bundle name: <product>_<target>.resources
COPY --from=build /build/.build/release/AbbeyServer_AbbeyServer.resources /app/AbbeyServer_AbbeyServer.resources
ENV HTTP_HOSTNAME=0.0.0.0
ENV HTTP_PORT=8080
EXPOSE 8080
CMD ["/app/AbbeyServer", "serve", "--hostname", "0.0.0.0", "--port", "8080"]
```

- [ ] **Step 2: Insert a web-build stage before the Swift build stage**

Replace with:

```dockerfile
# syntax=docker/dockerfile:1
# Build with official Swift 6.4 bookworm image (Linux) — must match Package.swift's
# swift-tools-version: an older toolchain's SwiftPM cannot parse a newer manifest.
# Leaf resources ship via SPM bundle. Dashboard SPA is built first so its static
# output exists on disk before the Swift build stage copies Sources/ (SPM's
# .copy("Resources") only picks up files already present at build time).

FROM node:22-bookworm-slim AS web-build
WORKDIR /web-build
COPY web/package.json web/package-lock.json* web/bun.lock* ./
RUN npm install
COPY web ./
COPY Sources/AbbeyServer/Resources ./sources-resources-placeholder
RUN npm run build

FROM swift:6.4-bookworm AS build
WORKDIR /build
COPY Package.swift Package.resolved* ./
COPY Sources ./Sources
COPY Tests ./Tests
COPY --from=web-build /Sources/AbbeyServer/Resources/Public ./Sources/AbbeyServer/Resources/Public
RUN swift package resolve
RUN swift build -c release --product AbbeyServer

FROM debian:bookworm-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates \
    libcurl4 \
    libssl3 \
    libsqlite3-0 \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=build /build/.build/release/AbbeyServer /app/AbbeyServer
# SPM resource bundle name: <product>_<target>.resources
COPY --from=build /build/.build/release/AbbeyServer_AbbeyServer.resources /app/AbbeyServer_AbbeyServer.resources
ENV HTTP_HOSTNAME=0.0.0.0
ENV HTTP_PORT=8080
EXPOSE 8080
CMD ["/app/AbbeyServer", "serve", "--hostname", "0.0.0.0", "--port", "8080"]
```

Note on the `web-build` stage: `vite.config.ts`'s `outDir: '../Sources/AbbeyServer/Resources/Public'` is relative to `web/` (Vite's project root). Inside the `web-build` stage, `web/`'s contents are copied to `/web-build`, so Vite resolves `outDir` to `/Sources/AbbeyServer/Resources/Public` (one level up from `/web-build`, at the container filesystem root) — this is why the `build` stage's `COPY --from=web-build /Sources/AbbeyServer/Resources/Public ...` step above references that absolute-looking path rather than `/web-build/Sources/...`. The `COPY Sources/AbbeyServer/Resources ./sources-resources-placeholder` line exists only so the `/Sources` parent directory exists in the `web-build` stage before Vite writes into it — without it, Vite's `emptyOutDir`/mkdir behavior may fail trying to create `/Sources/AbbeyServer/Resources/Public` from nothing. Verify this concretely in Step 3; if it turns out unnecessary, remove it (don't leave dead placeholder logic in if the build works without it).
